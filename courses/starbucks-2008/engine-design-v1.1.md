# 最小可复现模拟引擎设计（V1.1）

> 目标：先建立可审计、可回放、可产生分支差异的最小引擎，而不是假装已经拥有完整的商业世界模型。  
> 状态：设计规范；尚未声称已实现运行代码。  
> 适用案例：商业残局 01｜星巴克 2008。  
> 设计原则：确定性账本 + 有边界的不确定性 + 可解释的角色行为。

## 1. 引擎要解决什么

V1.0 的模拟反馈主要由叙事脚本生成，缺少统一状态转移机制。V1.1 的目标不是预测真实星巴克，而是确保：

1. 玩家行动会改变资源、时间、信息或经营状态；
2. 管理层、董事会、竞争者、员工和顾客不只是等待玩家提问；
3. 状态变化有可追溯的事件和规则；
4. 证据既可能支持也可能削弱玩家假设，不为戏剧平衡强行制造反证；
5. 相同初始状态、相同参数和相同事件序列可重复回放；
6. 不同策略可以产生不同路径，而不是无论如何都走向同一预设答案。

## 2. 架构：五层分离

### A. 历史事实层（H）

保存公开史料、原文摘录、发布日期、适用时间范围、来源URL和核验状态。此层不可由模拟引擎改写。

### B. 玩家信息层（K/S/U）

保存某一时点玩家可见的材料。每条材料记录：
- `evidence_id`
- `created_at_sim`
- `historical_publication_date`（可空）
- `player_available_at`
- `source_type`
- `evidence_class`：H/K/S/I/U
- `scope`、`sample`、`method`、`limitations`
- `supports` / `challenges` / `does_not_distinguish`
- `confidence` 或定性等级

### C. 世界状态层

保存市场、门店组合、顾客、员工、组织、资本项目和竞争环境的状态。世界状态包含可观测变量与隐藏变量。隐藏变量不能被直接展示给玩家，只能通过调查逐步获得信号。

### D. 行动与事件层

玩家、NPC和外部环境都通过事件改变世界。禁止直接在叙事回复里改状态而不写事件。

### E. 呈现层

将状态、证据、角色意见和行动选项转成自然语言、表格或界面。呈现层不能自行创造数值；数值只能来自状态层、事件层或明确标注的叙事性模拟材料。

## 3. 状态模型：只保留可解释的最小集合

首轮只使用以下状态域。数值范围和单位必须在每个变量定义中明确。

| 状态域 | 变量示例 | 说明 |
|---|---|---|
| 顾客需求 | 活跃顾客指数、到店频率、交易量 | 分开顾客规模与单客频率 |
| 门店体验 | 高峰等待、差错率、满意度 | 体验变量需明确观测窗口和样本 |
| 运营能力 | 单位时间处理量、排班覆盖、培训熟练度 | 区分产能、负荷和熟练度 |
| 产品复杂度 | SKU/定制复杂度、制作步骤、培训负担 | 复杂度本身不是坏事，需与顾客价值共同评估 |
| 门店组合 | 单店贡献利润、区域组合贡献、内部蚕食风险 | 不把单店收入直接等同增量收益 |
| 组织状态 | 执行负荷、变革能力、员工士气 | 变化需要事件依据 |
| 治理状态 | 董事会支持、项目审批状态 | 不是任意剧情分数 |
| 资本项目 | 投资额、承诺状态、退出成本、预期现金流 | 无数据时保持未知，不补造 |

**重要：** V1.1 不为所有变量编造统一公式。只有明确给出参数来源、单位、适用范围和不确定性的变量，才允许数值计算。其余变量使用区间、等级或“未知”。

## 4. 事件账本：所有变化的唯一入口

每个事件必须保存以下字段：

```json
{
  "event_id": "EVT-0001",
  "sim_time": "2008-01-08T09:00:00-08:00",
  "event_type": "player_action",
  "actor": "CEO",
  "action": "request_customer_cohort_analysis",
  "sequence": 1,
  "rules": [
    {
      "rule_id": "resource.charge",
      "inputs": {"cost": 1}
    }
  ],
  "evidence_ids": ["EVD-0001"],
  "parallel_group": null,
  "depends_on": [],
  "player_visible": true,
  "notes": "事件只提交规则输入，不直接填写状态差分"
}
```

字段约束：
- 状态差分只能由预先注册的规则函数计算；事件作者不得填写任意 before/after。
- 每个rule_id必须映射到可执行函数、不可变参数、输入约束和允许写入的状态字段。
- 规则注册表在分支运行前冻结；规则或参数变更必须创建新版本。
- uncertainty保存范围、概率或定性限制；不允许把点估计伪装成确定值。
- causal_links在运行记录中指向行动、证据和规则；不能只写“因为CEO要求”。
- 纯叙事事件允许rules=[]，且不得改变世界状态。
- 修订错误时追加更正事件，不覆盖历史事件。

## 5. 三种资源严格分账

### CEO决策精力

代表CEO有限的注意力和决策带宽。只在玩家授权、决策、重大沟通或要求高层分析时扣减。

### 日历时间

代表调查、沟通、审批、培训和执行实际占用的模拟时间。可并行的任务必须记录依赖关系和资源约束，不能简单把所有任务时间相加或全部重叠。

### 组织执行能力

代表团队同时承接变革的能力。它是容量/负荷，不是CEO决策点。多个项目并行时，可能导致排队、延期、质量下降或其他项目被挤出。

**禁止规则：** 不得把“决策精力为0”解释为世界停止；已授权项目可以继续执行，但新的CEO决策仍受限制。V1.0 MOVE 005 的执行观察应按这一规则解释。

行动成本计算：
1. 每个行动先拆成任务；
2. 每项任务明确负责人、开始条件、持续时间、精力成本、组织负荷；
3. 共享数据源或会议可以合并成本，但必须记录共享依据；
4. 玩家确认前展示估算成本；
5. 实际成本与估算不同时，记录差额和原因；
6. 不得在行动结束后追溯性修改成本规则。

## 6. 玩家行动流程

1. **理解指令**：保留玩家原话，不把自然语言改写成更强或更弱的承诺。
2. **拆解行动**：列出任务、负责人、目标、覆盖范围和依赖。
3. **检查权限与前置条件**：若缺信息或权限，提出最关键的澄清。
4. **成本预估**：显示决策精力、日历时间、组织负荷和潜在机会成本。
5. **玩家确认**：需要花费资源或改变经营状态的行动必须获得玩家授权。
6. **排程执行**：创建任务和事件，不立即跳到结论。
7. **释放证据**：只在任务完成或信息自然可得时向玩家展示。
8. **状态更新**：按规则计算或记录为未量化变化。
9. **复盘快照**：保存行动前后状态、玩家当时可见信息和未解决问题。

如果玩家自由提出规则中没有列出的行动，引擎应尝试拆解，而不是拒绝或强行映射到预设选项。

## 7. NPC自主性：目标、信息、权限、触发器

每个关键角色有独立档案：

- 职责和正式权限；
- 个人/部门目标；
- 绩效压力和激励；
- 可访问的信息；
- 对信息的信念与不确定性；
- 风险偏好；
- 不能接受的结果；
- 可采取的行动；
- 触发行动的条件；
- 与其他角色的利益冲突。

NPC行动只有在“目标受到影响 + 已获得相关信息 + 有权限/资源 + 触发条件满足”时才发生。没有行动也可以是合理结果。

### 竞争者模型

竞争者不是为玩家制造障碍的剧情工具。其行动取决于：
- 自身市场目标；
- 价格、产品、渠道、门店位置和营销能力；
- 对市场机会的判断；
- 竞争者能观察到的公开信号；
- 行动成本与预期收益。

竞争者不会自动知道玩家内部计划。其动作可与玩家行动无关，也可能因为市场机会而发生。

### 员工与顾客模型

员工反应受工作负荷、培训质量、排班、管理支持和激励影响；顾客反应受价格、体验、可达性、产品价值和替代选择影响。不得把顾客或员工写成同质群体。

## 8. 证据生成与反证纪律

证据由数据生成过程、抽样过程和信息可得性决定，而不是由“要不要给玩家一个反对意见”决定。

每个调查任务先定义：
- 目标总体；
- 抽样框；
- 抽样方法；
- 样本量；
- 指标定义；
- 观测窗口；
- 缺失机制；
- 潜在偏差；
- 可识别和不可识别的问题。

调查结果可以：
- 支持一个假设；
- 削弱一个假设；
- 同时支持多个解释；
- 无法区分竞争解释；
- 发现新的解释；
- 因样本或数据质量不足而没有结论。

没有数据时明确输出“未知”。禁止为了推动故事而生成确定性数据。

## 9. 不确定性与随机性

- 确定性计算优先用于资源账本、算术、排程和明确规则。
- 随机事件只用于真正不确定的外部或行为过程。
- 每次随机抽样记录算法、种子、抽样空间和时间。
- 如果暂时无法保存随机种子，至少保存实际抽取结果与抽取规则，保证棋谱可回放。
- 对模型参数使用范围或情景，不使用未经校准的伪精确小数。
- 任何AI推演均标 I，不升级为历史事实。

## 10. 分支、快照与回放

在以下节点保存快照：
- 玩家提交重大决策前；
- 决策执行后；
- 新证据改变关键假设时；
- 外部冲击发生时；
- 最终战略陈述前。

分支包含：
- 父快照ID；
- 改变的决策；
- 保持不变的初始条件；
- 新事件序列；
- 分支差异；
- 不可比条件。

反事实分析必须说明哪些条件被固定、哪些条件随决策变化。不得将两个条件不同的分支简单归因于一个单独行动。

## 11. 最小运行循环（伪代码）

```text
load snapshot
while simulation_not_ended:
    ingest_player_instruction_or_due_event()
    parse_into_candidate_actions()
    validate_permissions_and_preconditions()
    estimate_cost_and_show_to_player()
    if player_authorizes:
        append_action_event()
        schedule_tasks()
    resolve_due_tasks()
    evaluate_npc_triggers()
    resolve_external_events()
    release_only_available_evidence()
    apply_validated_state_transitions()
    run_invariant_checks()
    save_snapshot_and_event_log()
    render_player_view()
```

呈现模型不能直接改状态。状态变化必须通过 `apply_validated_state_transitions` 并生成事件账本记录。

## 12. 首批自动化验收测试

### T1｜资源账本守恒

给定初始决策精力12，逐项加载V1.0成本记录。系统应检测MOVE 003显示成本2与余额差额3冲突，标记冲突，不自动覆盖原始记录。

### T2｜收入恒等式

当交易指数为100.4、客单价指数为104（共同基准100）时，收入指数应按定义计算为：

`100.4 × 104 / 100 = 104.416`

若显示为104.4，必须注明四舍五入规则；若基准期不同，则拒绝直接计算。

### T3｜顾客交易分解

当活跃顾客指数96、单客频率指数95，交易量指数可按同基准乘积计算为91.2。系统必须区分顾客规模下降和频率下降，不能直接写“永久流失”。

### T4｜证据限制

给定非随机20家门店归因分类9/6/5，系统不得输出“全美门店蚕食率45%”或“竞品导致30%下降”。只允许陈述样本内初步分类，并展示外推限制。

### T5｜培训试点因果边界

给定12家试点与12家非随机对照，且经理主动性和排班变化存在差异，系统只能输出描述性差分，不得自动输出培训的因果效应。

### T6｜资源与执行独立

当CEO决策精力为0，但已批准培训项目仍在执行队列中，系统允许项目继续；新决策行动需要新的授权/资源规则。

### T7｜策略分支差异

从相同初始状态建立两个测试分支：
- A：立即全面精简产品并快速扩张培训范围；
- B：先进行小范围流程实验、保留产品组合并延后扩张决策。

系统不预设哪条路径更好，但必须能展示两者在组织负荷、证据质量、执行时间和机会成本上的不同。如果两条路径最终完全相同，测试失败。

### T8｜NPC自主性

当竞争者观察到公开市场机会且自身收益条件满足时，可以在玩家没有要求时采取行动；当触发条件不满足时，不应为“增加戏剧性”强行行动。

### T9｜历史信息防泄漏

模拟时间早于某条历史材料公开时间时，玩家界面不得显示该材料为已知信息，除非有独立证据证明其此前已可获得。

### T10｜可回放性

相同初始快照、相同参数、相同事件顺序和相同随机种子应生成相同状态。更正通过新事件追加，不能覆盖旧事件。

## 13. 分阶段实施

### V1.1：档案与规则审计
完成时间线、角色、数据口径、资源账本、证据字段规范。保留V1.0原始棋谱。

### V1.2：最小可复现引擎
先实现事件日志、状态快照、资源结算、行动排程、证据发布和回放。NPC行为先用少量明确触发器，不急于做复杂Agent。

### V1.3：双策略压力测试
用相同初始条件重开第一课，分别测试不同战略路线，检验世界是否真正响应不同决策。

### V2.0：抽象可复用课程框架
第一课通过验收后，再把通用机制抽象到其他商业案例。不要过早把未验证规则抽象成通用框架。

## 14. 当前未解决的问题

- V1.0部分数据缺少原始抽样框、变量定义和观测窗口，不能靠引擎补齐。
- 真实星巴克门店层面的内部数据不可得，模拟不能宣称历史精确重建。
- 状态模型的参数需要明确标为课堂假设，并通过玩家体验测试调整。
- 引擎实现技术选型、持久化格式和测试执行环境尚未决定。


## 15. V1.2实现补充（与运行代码一致）

V1.2把原型中的作者填写状态差分改为规则注册表：
- RuleRegistry 将 rule_id 映射到可执行函数与预登记参数；
- Event 仅携带 RuleInvocation(rule_id, inputs)，不再接受作者直接填写的状态 before/after；
- 规则函数返回状态更新，内核检查目标字段、类型和资源不变量；
- 未注册的rule_id、未知状态字段和不满足前置条件的输入必须失败。

### 15.1 并行事件的确定性提交

日历任务可以重叠执行，但状态变更必须有可重放的提交顺序。V1.2按 sim_time → sequence → event_id 排序；依赖由 depends_on 显式声明。该顺序只定义账本提交顺序，不表示任务执行本身串行。未来若需要原子并行批次，需单独实现冲突检测和同快照合并，不可用叙事约定代替。

### 15.2 指数与证据护栏

IndexValue 必须携带基期和基准值；不同基期拒绝计算。证据评估返回设计等级，不自动把随机化标签等同因果证明。培训试点中的经理主动性与排班变化作为已知混杂因素保留。

### 15.3 对手触发审计

evaluate_triggers 对每个触发器写入检查时间、条件结果、动作或未行动原因。未触发记录与触发记录同等重要。

### 15.4 真实棋谱fixture与边界

首个fixture回填V1.0 MOVE 001–005。MOVE 003的成本冲突按历史记录保留；MOVE 004包级成本保留，但子行动成本分配缺失。fixture是旧棋谱的审计载入，不代表所有经营状态都已被公式化，也不代表这些S类数据获得了历史真实性。

### 15.5 双策略测试的解释限制

T7使用V1.0真实初始治理状态（决策精力12、董事会信任7、组织执行能力8、品牌信任指数100、员工士气指数100）建立两条策略路径。额外的执行负荷、培训覆盖和证据质量字段是引擎计数器；策略规则参数为预登记课堂假设，不是经星巴克真实数据校准的因果模型。测试证明规则响应不同输入并形成不同轨迹，不证明哪条策略在真实历史中更优。
